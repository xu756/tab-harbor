# Harbor 设计原则

Harbor 是浏览器里的安静工作台。界面目标是帮助用户快速看清当前状态、整理浏览上下文并回到工作，而不是吸引注意力到界面本身。

## 产品气质

设计保持三个关键词：

- **Calm**：低噪声、低眩光，不使用高饱和霓虹或大面积装饰。
- **Composed**：信息有明确层级，操作位置稳定，状态反馈克制。
- **Local**：交互像浏览器原生工具一样直接，不使用账号、增长或后台管理式表达。

视觉上接近一张安静的阅读桌：暖中性色表面、少量强调色、清楚的文字层级、紧凑但不拥挤的内容行。

## 信息结构

1. 先展示用户要处理的内容，再展示工具栏和统计信息。
2. 用标题、留白、分隔线和图标建立层级，避免把每组内容包装成独立卡片。
3. 同一区域只保留一个强主操作，低频操作收进次级按钮或菜单。
4. 列表优先保证扫读速度；描述文字只有在消除歧义时出现。
5. URL 等辅助信息可以参与搜索和编辑，不必在每一行持续占用视觉空间。

## 排版和密度

- 全局正文应在常见桌面距离下无需费力阅读。
- 标签行保持约 40 px；书签行保持约 48 px，为拖拽和行内操作预留空间。
- 标题通过字号和字重建立层级，不依赖夸张尺寸。
- 文字截断必须保留可识别的名称开头，并通过合理的容器宽度减少无谓截断。
- 1280、1440、1920、2K 和 4K 宽度下限制内容最大宽度，避免列表被横向拉散。

## 颜色和表面

- 使用 `background`、`foreground`、`muted`、`accent`、`border` 等语义 token，不在功能组件中随意加入孤立颜色。
- Light、Dark 和 System 主题共用相同的信息层级。
- 阴影只用来表达浮层或少量空间关系，普通内容分组优先用边框和表面色。
- 网站图标是列表中的主要身份线索；装饰图标不与其争夺注意力。

## 控件和反馈

- 优先组合 `src/components/ui/` 中的 shadcn 组件，交互原语使用 Base UI。
- 主操作始终可见；关键能力不能只在 hover 时出现。
- 所有可操作元素都有可见的键盘焦点、清楚的 accessible name 和足够点击区域。
- 空状态说明当前原因，并给出一个真实可执行的下一步。
- 加载、成功和错误状态就近显示，不使用夸张的全局动效。
- 动画以 150–200 ms 的淡入、位移或旋转为主，并支持 `prefers-reduced-motion`。

## 响应式布局

新标签页是主要入口，Side Panel 是次要入口，但两者需要达到同等的可用性标准：

- 多列布局在窄宽度降为单列。
- 双栏资源管理器在窄宽度改为上下结构。
- 导航保留图标并收起文字，不能因为空间不足失去页面入口。
- 控件换行时保持阅读顺序和键盘顺序一致。
- 固定高度区域必须提供内部滚动，不能让操作栏离开可见范围。

## 书签资源管理器

- 左侧文件夹树负责定位，右侧列表负责查看和操作当前层级。
- 缩进、展开箭头和文件夹图标共同表达层级，不额外绘制复杂树线。
- 当前文件夹和拖拽目标必须有不同且明确的状态。
- 拖拽是快速路径，“移动到”选择器是键盘可达的完整路径。
- 普通书签行只显示名称；网址在编辑时显示，并继续参与全文搜索。

## 评审问题

提交 UI 变化前，用以下问题快速检查：

1. 用户能否在几秒内找到页面的主要内容和主操作？
2. 去掉某个边框、卡片、说明或图标后，信息是否仍然清楚？
3. 键盘和触控板用户能否完成同一项关键任务？
4. 动画关闭后，状态变化是否仍然可以理解？
5. 该页面在新标签页和 Side Panel 中是否都可用？
6. 视觉是否仍像阅读工作台，而不是 SaaS 仪表盘或卡片墙？
